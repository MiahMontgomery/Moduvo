Moduvo Platform Full-Stack Deployment Plan

Moduvo aims to deliver a high-end, luxurious experience for modular installations. This plan outlines the complete system – from a polished frontend to a robust backend – as a Replit project that can be deployed on a Contabo VPS. We cover each requirement in detail, including AR functionality, 3D asset handling, authentication, quoting, admin CMS, and deployment.

Frontend: React, Tailwind & Premium UI Design

The frontend will be built with React and styled with Tailwind CSS to achieve a modern, responsive design. Tailwind’s utility classes enable quick design iterations and consistent styling. We will emphasize an enterprise-grade look: a clean layout, ample whitespace, and elegant typography reflecting luxury branding. Both mobile and desktop experiences are optimized via responsive design breakpoints in Tailwind.
	•	Smooth Transitions & Animations: We’ll use Tailwind’s built-in CSS transitions and animation utilities for subtle interactions (e.g. button hover glow, dropdown menus)  . Complex animations such as page fade-ins or element slides can be achieved with libraries like Framer Motion in React, ensuring animations convey premium quality without overwhelming the user. Micro-interactions (like a gentle card hover lift or a pulse effect on CTAs) will reinforce a high-end feel. All animations will be motion-safe (respecting users’ reduced-motion preferences) .
	•	Modern Components: The UI will incorporate contemporary design elements: a sticky navigation bar with a transparent background that becomes solid on scroll, a hamburger menu for mobile, and a cohesive color scheme aligning with Moduvo’s brand. We’ll use React component libraries or custom components for elements like carousels (for the Gallery), modals, and tabs. Each component will be styled with Tailwind for consistency. Interactive components (like form inputs, configurators) will have clear focus states and error handling, balancing form with function.
	•	Responsive & Mobile-First: The layout uses a mobile-first approach, ensuring content is easily navigable on phones (since the AR feature is mobile-centric) while scaling up elegantly to larger screens. Tailwind’s grid and flex utilities will create flexible page sections that reflow appropriately on different devices. Touch-friendly elements (large buttons, swipeable carousels) will enhance mobile UX.
	•	Premium Aesthetics: To convey luxury, the design will use high-quality images (in Gallery and backgrounds), possibly subtle gradients or dark mode elements for a sleek look, and smooth scroll effects. Transitions between pages or sections might use fade or slide animations (e.g. using CSS transition-opacity or React route transition libraries) to give a polished feel. The homepage hero could feature an autoplay looping video or image with a slow zoom, overlaid by a bold tagline.

Interactive AR Product Viewer (WebXR + Three.js)

One standout feature is the Live VR/AR Viewer, allowing users to visualize modular units in their own space via augmented reality. We will implement this using WebXR (for AR capabilities in-browser) combined with Three.js for rendering the 3D models:

Illustration: A user placing virtual modular furniture in their real room using a smartphone (conceptual AR view).
	•	WebXR for AR: The WebXR Device API enables immersive AR experiences directly in the mobile browser  . We will integrate a WebXR session that activates the device camera and motion sensors, overlaying 3D content into the real world. This feature will be prominently accessible on the “Visualize” page via a “Start AR” button. We will leverage Three.js’s helpers like ARButton to enter AR mode. Using ARButton.createButton(renderer, { requiredFeatures: ['hit-test'] }), we ensure the app only runs on devices that support AR hit-testing (surface detection) . Chrome for Android is our primary supported platform, as WebXR AR is best supported on Android browsers (with iOS support still emerging) .
	•	Three.js Rendering: In AR mode, Three.js will render the product models into the live camera feed. We’ll set up a Three.js scene, camera, and lighting. The camera’s pose is controlled by WebXR (mapping to the device’s real-world orientation), while the virtual objects will appear anchored in the physical space. We will utilize hit-testing to place objects on real surfaces: when the user taps on a point in the camera view, a raycast/hit-test will find the real-world plane and position the 3D model there. Three.js provides an XRHitTestSource via WebXR that we can use to get placement positions in the real world .
	•	Placing & Manipulating Objects: Users can drag or reposition the modular unit in AR. This can be done by detecting touch events in AR mode – e.g., using Three.js raycasting to pick the model and move it as the user drags their finger. Three.js has example implementations of dragging objects in AR . We will replicate that functionality so the product can be translated on the floor or wall. Additionally, we’ll allow simple rotations (e.g., two-finger twist to rotate the object).
	•	Customization in AR: The AR viewer will reflect customizations in real-time. For example, if the user toggles a color or adds a component (shelf or drawer) in the UI, the 3D model in AR will update: we might swap the material on the model (for a color change) or toggle the visibility of certain mesh groups (for adding/removing components). This dynamic update will be facilitated by maintaining references to the Three.js mesh objects and adjusting them based on UI controls.
	•	Fallbacks: Since not all users may have AR-compatible devices (notably, WebXR is not fully supported on iOS Safari yet ), our app will detect support and gracefully degrade. If AR is unsupported, the Visualize page will display a message (e.g. “AR is not supported on this device/browser” and perhaps offer a QR code or link to open on a compatible device). We can use navigator.xr checks or Three.js’s AR support check (as shown in their examples)  to implement this. We will also include helpful instructions (maybe an onboarding overlay) on how to move the device to scan the room for surfaces, guiding the user in AR usage.

3D Asset Management with glTF Models

To showcase modular products in 3D (for both AR and on-screen previews), we will use glTF/.glb 3D models for each component and configuration. glTF is an efficient, modern 3D asset format that includes geometry, materials, and textures and is well-supported by Three.js’s GLTFLoader . Key aspects of our 3D asset pipeline:
	•	Modeling & Composition: The modular furniture (likely based on IKEA dimensions but rebranded) will be modeled in a 3D tool (e.g. Blender) and exported to glTF. Each product (e.g., a wardrobe or cabinet system) might be composed of sub-parts: frames, shelves, drawers, doors, etc. We can either export a full assembly model with optional parts or separate models for each part and assemble them in Three.js. For flexibility in toggling components, we might import each piece separately and then programmatically combine them (parenting to a group), or use glTF extras/variants. Another approach is to have all possible parts in one model and hide/show parts as needed.
	•	External Storage via CDN: These 3D assets will be stored externally for performance and scalability. We can use an S3 bucket or Cloudflare R2 (which is S3-compatible and has no egress fees ) to store the .glb files. This allows the Replit app or backend to fetch models via CDN URLs. For example, a model might be accessible at a URL like https://cdn.moduvo.com/models/wardrobe.glb. Using a CDN ensures quick download times, especially important for potentially large 3D files. Supabase also offers an Object Storage service which is S3-compatible , so we could integrate that – storing models in Supabase storage (which in turn uses CDN caching) and retrieving via signed URLs or public URLs as appropriate.
	•	Loading in Three.js: On the Visualize or Customize page, when a user selects a particular product configuration, the app will load the corresponding glTF model using Three.js’s GLTFLoader. For example:

import { GLTFLoader } from 'three/examples/jsm/loaders/GLTFLoader.js';
const loader = new GLTFLoader();
loader.load(modelUrl, (gltf) => {
    scene.add(gltf.scene);
});

The above code snippet shows how a glTF file is loaded and its scene graph added to our Three.js scene . We will manage loading states (show a spinner or progress bar while models download). Models will be scaled and oriented correctly (e.g. 1 unit = 1 meter in Three.js for realistic AR scale ). We will add appropriate lighting (ambient and directional lights) so that materials (finishes like wood grain, metal) appear realistic  .

	•	Optimizing Assets: To ensure smooth performance on mobile, models should be optimized (moderate polygon count and compressed textures). We can use Draco compression or Meshopt for glTF if needed. Also, not all models need to load at once – we can lazy-load models when a user selects them. If multiple color variants exist, it may be more efficient to load one model and swap its material color rather than separate files.
	•	Asset Metadata: We’ll maintain a catalog of products and parts in the database. For example, an entry for “Modular Wardrobe A” might list available widths, finishes, and compatible add-ons. Each variant can link to a model file URL. This way, the front-end can dynamically fetch the right model based on user choices (perhaps even assembly multiple glTFs together for a custom configuration).

User Authentication & Accounts

The platform will include basic authentication so that users can create accounts, save their room designs, and retrieve quotes. We have two main options, but we’ll prioritize Supabase for its integrated Auth and database services:
	•	Supabase Auth: Supabase provides an out-of-the-box user authentication system (email/password, OAuth providers, etc.) through its GoTrue service . We will use Supabase’s JS client (@supabase/supabase-js) on the frontend to handle signup, login, and session management. This means we won’t have to implement password storage or verification ourselves – Supabase will handle securely storing hashed passwords and issuing JWT tokens for authenticated requests. A new Supabase project comes with a ready-made auth.users table for user accounts . Using Supabase’s React libraries, we can quickly set up an auth UI or build custom forms. For example, the Supabase React Quickstart shows how to initialize the client and either show an <Auth> component or the app when session exists .
	•	Auth UI/Flow: We’ll include an Account page in the UI. This page will allow users to sign up or log in, and once logged in, view their saved configurations and quote history. The sign-up form will collect basic info (name, email, password). Supabase supports email confirmation if desired. After authentication, we use a context or state in React to store the user session (e.g., with supabase.auth.onAuthStateChange and supabase.auth.getSession() to persist login ). Auth-protected routes (like viewing saved designs) will check for a valid session; if not present, the user is prompted to log in.
	•	Data Privacy & Isolation: Each user’s saved designs and quotes will be stored in the database associated with their user ID. If using Supabase, we can enforce Row Level Security (RLS) policies to ensure users can only access their own data. Supabase’s integration of JWT auth with Postgres RLS means we can create policies like CREATE POLICY "user_can_select_own" ON designs FOR SELECT USING ( auth.uid() = user_id ); so that each query automatically filters to their own user_id  . Supabase recommends always enabling RLS for secure data access , which provides end-to-end security from browser to database . This way, even if someone knew an API endpoint, the database would not return someone else’s data as long as RLS is in effect and properly configured.
	•	Alternative (Express + JWT): If we opt for a custom Node/Express backend instead, we would implement auth using a library like Passport.js or bcrypt + JWT. The flow would be: user signs up -> backend hashes password and stores user in a Postgres DB -> on login, verify and return a JWT. That JWT would be used to authenticate subsequent API calls (sent in an Authorization header). Given the time and complexity, Supabase’s pre-built auth is preferable, but a custom solution provides more control if needed. In either case, passwords must be hashed (e.g. bcrypt) and the system should use HTTPS and secure cookies or tokens to protect user sessions.
	•	Account Features: Authenticated users can save room configurations (e.g., save the arrangement of modules they created, possibly store as a JSON of design specs or a set of chosen components). They can also save multiple designs and request quotes for each. This data will be linked to their account. On the “Account” page, they’ll see a list of “My Designs” and “My Quotes.” Clicking a design could reload the configuration in the Customize page for editing. Quotes might be listed with status (e.g., “Estimate”, “Finalized after site visit” etc., if such workflow exists). Basic profile management (update name, etc.) can be offered but is secondary.

Modular Customization & Quote Engine

One core business feature is the instant quote engine which calculates an estimated price for the user’s custom modular install. This will tie together data from the selected components, materials, and external factors like location. Here’s how we will implement it:
	•	Customization UI: The “Customize” page will present options to configure a product. First, the user might choose a base unit (for example, a wardrobe frame of certain dimensions). Then they can customize aspects:
	•	Dimensions: If applicable, select width/height/depth or choose from standard sizes.
	•	Finish/Color: Choose surface finishes (e.g., white, oak, walnut veneer, etc.).
	•	Components: Toggle sub-components like shelves, drawers, doors. For example, an option “Add 2 drawers” or “Include shoe rack module”. When toggled, the 3D preview updates (if not in AR, we will still show a 3D model in the browser using Three.js or possibly a simpler 2D illustration if needed).
	•	Hardware/Accessories: if relevant, select knob styles or lighting kits, etc.
The UI for this could use an interactive form or even a drag-drop interface (though that adds complexity). Likely a form with visual previews: e.g., small thumbnail images for each finish or component type. Selections update the price dynamically and also feed into the AR/3D viewer.
	•	Quote Calculation: The Quote page (or a section on the Customize page) will display the price estimate. The calculation will factor in:
	•	Materials Cost: We’ll maintain a base cost for each component (e.g., each shelf is $X, each drawer is $Y, different finishes might have cost multipliers). We might have a cost table in the database for raw material costs or use average prices from the IKEA baseline.
	•	Labor Installation Cost: We use average installation effort required for the selected configuration. For instance, each cabinet frame might take N hours to install, each additional component adds some time. We can use average labor rates for Toronto/GTA – say an installer rate (e.g., $50/hour as a rough figure, or use data like average cost per linear foot). These rates can be calibrated from industry data or kept adjustable in the admin panel.
	•	Transport/Logistics: Based on the provided location (postal code), we can estimate a delivery cost. For simplicity, we might define zones (e.g., within Toronto proper vs outer GTA). A postal code can be mapped to a zone or distance from our warehouse, and we charge a fixed fee or per-km fee. Alternatively, assume a flat delivery fee within GTA and higher outside.
	•	Markup for Profit Margin: We need to ensure a net 38% profit margin on the final price. This means the quote should be set such that (Price - Cost)/Price = 0.38 (i.e. profit 38%). Equivalently, Price = Cost / (1 - 0.38) . For example, if total estimated cost (materials + labor + transport) is $1,000, then Price = 1000/0.62 ≈ $1613 to yield ~38% margin. We will incorporate this calculation in the quote engine. Essentially, we sum up all costs as Cost of Goods Sold, then apply the formula to get the quote price. (This is different from a simple 38% markup on cost; it’s a margin target  .)
We will present the breakdown to the user for transparency: e.g., “Materials: $X, Labor: $Y, Delivery: $Z, Total: $Quote (includes overhead & margin).” The user can then choose to save this quote or proceed to contact sales.
	•	Implementation: The quote engine logic can reside in the backend (ensuring it remains consistent and not tampered with on the client). For instance, when the user hits “Get Quote”, the frontend sends the selected configuration (component list, location, etc.) to a backend API endpoint /api/quote. The backend then:
	1.	Looks up cost data for each selected item from a database table (e.g., a table of component costs and labor requirements).
	2.	Calculates subtotal cost of materials.
	3.	Calculates labor cost: possibly labor hours required times a rate. We could have a small algorithm, e.g., base install time + per component time.
	4.	Calculates delivery: either a simple lookup by postal code region or using an external API for distance (though likely not needed for an MVP; a lookup table is sufficient).
	5.	Sums these to get total cost.
	6.	Applies the margin formula to compute final price.
	7.	Returns the price (and optionally the breakdown).
On receiving this data, the frontend displays it nicely. We will also store the quote in the database (with a reference to the user and configuration) if the user is logged in, so they can review it later. If the user is not logged in, we might prompt them to create an account to save the quote (they can still see the price estimate without logging in, but to persist it or proceed to booking we’d need their info).
	•	Toronto/GTA Data: We will use Toronto-specific averages where possible to make the estimates realistic for that market. For instance, if average installation of a PAX wardrobe (IKEA analog) in Toronto is known to be, say, $300 for labor, we can align our calculations roughly. We may also factor taxes (e.g., show that it’s before HST). These specifics can be adjusted in the admin panel as we gather more accurate data.

Backend: Supabase (Postgres) &/or Node.js Server

For the backend, we have a couple of options, but the recommended approach is to utilize Supabase for most heavy lifting (database, auth, storage) and possibly a lightweight Node/Express server for custom logic:
	•	Database (PostgreSQL): We will use a PostgreSQL database to store persistent data:
	•	Users: If using Supabase Auth, user info is in auth.users. We can have a public profiles table linked via user ID for additional info like name, etc.
	•	Products/Components: Tables describing the modular products (with fields like name, base_price, etc.) and components (with type, cost, etc.). This is the master data for the configurator.
	•	Designs/Configurations: A table that stores a user’s saved design. It might include a JSON structure or a set of relational links (e.g., a design table with an ID, user_id, and perhaps a JSON field of { productType, components: […], finish: X, dimensions: Y }).
	•	Quotes: Table storing quotes generated, including foreign key to design (if any), user_id, calculated price, breakdown fields, date, etc.
	•	Leads/Requests: If a user proceeds to request a formal quote or consultation, we record it (this might overlap with quotes or be separate).
Using Supabase, we manage this via their interface or SQL scripts. Supabase allows defining relationships and even building APIs directly via PostgREST (each table can be accessed through RESTful endpoints secured by RLS).
	•	Supabase vs Express API: Supabase offers a direct database API (via PostgREST and GraphQL). For many CRUD operations (saving a design, retrieving products), we could use Supabase’s JS client to call these endpoints. For example, to save a design: supabase.from('designs').insert({ user_id: ..., config: {...} }). This would require proper RLS so users can only insert/select their own records. This approach can eliminate the need for a separate server for basic operations. For more complex logic (like the quote calculation), we have options:
	•	Write a Supabase Edge Function (serverless function in Deno) to perform the calculation on request.
	•	Or, stand up a small Express/Node server (running in the Replit environment) that handles certain endpoints (like /api/quote as described).
Given the prompt suggests Supabase or Express, we can choose Supabase for simplicity and reliability. We might still have an Express server if needed for SSR or serving the React app (if not purely static). In Replit, we can indeed run a Node server that serves the built React frontend and also has API endpoints. On Contabo, we could do the same or host the React static files on Nginx and an API on Node. But a single Express backend could serve both API and static content.
	•	Supabase Advantages: Supabase being a Firebase-alternative means we get easy integration: authentication is integrated with database security (as noted with RLS) , and we have file storage for user uploads (e.g., if we allow users to upload a photo of their room or a screenshot of their AR view for reference). The storage API is S3-compatible , so it’s perfect for storing assets or user files with minimal backend code.
	•	Avoiding Firebase: The instructions say avoid Firebase, which is fine as Supabase covers our needs in an open-source way using Postgres . We get relational power (easy to do joins, complex queries for analytics like seeing most popular components, etc.). If we needed serverless functions, Supabase’s Edge Functions can be used, or we simply use Node.
	•	Express/Node (if used): If we include a Node backend, it will be a minimal layer:
	•	Serve the React app (if we aren’t deploying separate).
	•	Provide endpoints like /api/quote, /api/sendLead (to email the company or notify admin of a new quote request), etc.
	•	Possibly handle integration with any third-party services (for example, an email service to send confirmation emails or scheduling installation).
This Node server will use the Supabase client or direct PG queries to interact with the database. Alternatively, since we have direct DB access on the server side, we could use an ORM like Prisma or Knex to query the Postgres DB. But to keep it simple, we might just use Supabase client even from the server, or use node-postgres driver with connection string from Supabase (Supabase provides a DB connection string too).
	•	Supabase Security: We will store the Supabase API keys securely (the anon public key can be in frontend for normal calls, the secret service role key if needed only on backend). All Supabase calls will be over SSL. We will enable RLS on tables with policies as discussed to ensure security even if the anon key is used on frontend (no data leakage). Supabase Auth JWT will be automatically used by the client to authenticate requests (the supabase client attaches the token to queries).

Admin Panel (CMS for Moduvo)

To manage content and leads, we will implement a lightweight admin panel. This could be a separate section of the React app accessible only to admin users (e.g., behind an admin login). Simplicity and security are key here:
	•	Admin Authentication: We can designate certain accounts as admins (for instance, using Supabase Auth’s user metadata or a role field in a profiles table). The admin panel will check the logged-in user’s role; if not admin, deny access. Alternatively, have a separate login for admins (even basic HTTP auth on the admin route as an extra layer, if desired).
	•	Functionality: The admin panel will provide:
	•	Lead Management: View a list of leads or quote requests. When a user saves a quote or explicitly submits a “Contact me” request, it will appear here. Fields might include user info, their configuration summary, quote amount, timestamp, and a status (e.g., New, Contacted, Converted). Admin can update the status or add notes (e.g., “Called client on 2025-08-15, scheduled site visit”).
	•	Room Captures: If the platform allows users to upload images of their room or AR snapshots for consultation, those images (or links to them in storage) would be listed. Admin can click to view the image, presumably to understand the client’s space.
	•	Saved Configurations: Possibly the admin can pull up any user’s saved design by ID to review what components they chose. This helps when discussing with the client.
	•	Content Management: Manage the Gallery items (upload new high-res photos or embed videos of installations). We could integrate a simple interface to add gallery entries (with image upload to storage and text captions). Also possibly manage product data: e.g., an admin could update prices or add a new finish option through a form that writes to the products/components tables. However, heavy CMS capabilities may be overkill – initial data can be seeded in the DB. But having at least a way to update costs (like labor rate or profit margin target) via an admin interface would be convenient. We can have a “Settings” section for such financial parameters.
	•	Implementation: We might use an existing admin template or just quickly scaffold something with a UI library. Since we’re already using React + Tailwind, we can create admin pages with tables and forms. For example, a “Leads” page that lists entries from a leads table. We can retrieve those via Supabase (with service role key on backend or RLS policies granting read to admin). We can also integrate simple charts (e.g., number of quotes per month, conversion rate) using a chart library for a dashboard feel.
	•	Admin Panel Security: Ensure that only authorized accounts can access it. This likely means checking user.role === 'admin' in our React route guard. Also, on the backend, enforce that admin APIs (like updating product pricing) only execute if the request is by an admin (we can verify the JWT token’s email against an allowed list or have an admin claim). Supabase could also handle this by separate policies or using the service key for admin actions with caution. Additionally, since the admin panel deals with potentially sensitive user data, we will host it under a secure path (e.g., /admin) and ensure all requests are HTTPS and preferably with short sessions or re-auth requirements for safety.
	•	Alternative CMS: If time permitted, one could integrate a headless CMS (like Strapi or Directus) for content and leads management. But given the scope, a custom built-in admin is simpler and keeps data in our database. Supabase’s own dashboard (Supabase Studio) can also be used internally to view and edit tables, but that’s more for developers than a client-friendly admin. We’ll proceed with a custom admin UI tailored to Moduvo’s needs.

Site Structure & User Flow

The app will have a clear navigation and pages as specified:
	1.	Home: This is the main landing page. It will feature a strong brand statement/tagline (e.g., “Elevate Your Space with Moduvo Modular Designs”), a visually rich hero section (image or looping background video of a luxury modular installation). A prominent Call-to-Action (CTA) here encourages users to start visualizing their own project (“Try our AR Visualizer” button) or get a quote. We’ll highlight key value propositions (premium quality, custom fit, professional installation) in a few eye-catching sections. Smooth scroll animations will reveal content as the user scrolls (using Tailwind CSS transitions or small JS for on-scroll reveal).
	2.	Gallery: A showcase of sample installs. This page will contain a grid or carousel of high-resolution photos and possibly short video clips of completed projects. For example, living room built-ins, custom wardrobes, office shelving systems – many likely derived from IKEA systems but customized. To avoid explicitly naming IKEA, we present them as Moduvo projects. Each gallery item will have an alt-text describing it (good for SEO , e.g., “Luxurious walk-in closet system with walnut finish by Moduvo”). Users can click on a photo to enlarge it (lightbox style) and see details. We might also include testimonials or brief descriptions per project. Ensuring image files are optimized (using modern formats like WebP and lazy-loading offscreen images) will maintain performance.
	3.	Visualize: This launches the AR experience. On desktop, we might show a prompt with a QR code or a message to open on mobile (since AR requires a camera). On mobile (Android Chrome), this page will show the “Start AR” button provided by Three.js’s ARButton  . Tapping it will enter AR mode full-screen. We will overlay a simple UI in AR mode: possibly a “place object” hint, and basic controls like rotate or remove object, and an exit AR button. The user can switch among different products or finishes while in AR through a small UI menu or by exiting back to Customize page.
	4.	Customize: This is the interactive 3D configurator page (for non-AR preview and selecting options). It can share similar functionality with the AR page but presented in a more traditional interface. On this page, we will show a 3D model viewer (using Three.js but not in AR mode, just a standard OrbitControls camera). The user’s selections (from dropdowns, color pickers, toggles) will update the model in this viewer. For instance, selecting “Walnut finish” will change the material to a walnut texture, adding a component will call a function to add that mesh into the scene, etc. This gives users who can’t use AR a way to visualize in 3D. We’ll also display dimensions and maybe allow basic interactions like zoom, rotate model. Once the user is satisfied, they can click “Get Quote” which takes them to the Quote page.
	5.	Quote: This page shows the breakdown of the pricing calculation done by the quote engine. If arriving here after customizing, the data will be pre-filled (we’ll likely navigate to Quote and pass along an ID or context of the configuration). The quote is displayed with line items (materials, labor, transport) and the profit margin inclusion, culminating in the final estimated price. There will be a note that this is an instant estimate and might be refined upon an in-person assessment (if that’s the business flow). The user (if logged in) can save the quote to their account. If not logged in, we may prompt “Enter your email to save this quote and have a Moduvo representative reach out.” This doubles as lead capture. Another CTA here could be “Request Free Consultation” which notifies admin to follow up. In such case, we record it as a lead with the quote attached.
	6.	Account: A personal dashboard for the user. If not logged in, this page will show a login/register form. If logged in, it will show:
	•	Profile info (name, email, etc, with ability to edit perhaps).
	•	Saved Designs: a list of their saved configurations (if any). Selecting one can take them back to Customize with that design loaded.
	•	Quote History: a list of quotes they have generated. Possibly including whether they requested follow-up, or any notes (e.g., “Consultation scheduled on…”, which an admin might add on their behalf unless we allow user to also input).
	•	Possibly a way to upload room measurements or photos (if we want to gather that pre-consultation).
	•	Option to log out.
This page ensures repeat users can come back and see their past interactions, reinforcing engagement.

Navigation between these pages will be via a header menu (Home, Gallery, Visualize, etc.) and user account icon for Account page. The CTAs in various pages will guide the user flow (Home -> Visualize -> Customize -> Quote -> Account to save). We will make sure the route changes update the page metadata (using react-helmet or similar) for SEO so each page has an appropriate title and meta description (e.g., Gallery page meta description about “See examples of Moduvo installations…”)  .

SEO, Performance, and Branding Considerations

To attract organic traffic and provide a polished presence, we will implement strong SEO and branding practices:
	•	Meta Tags & Titles: Each page will have descriptive titles and meta descriptions containing relevant keywords (e.g., “Moduvo Gallery – Luxury Modular Furniture Installations in Toronto”). Using React Helmet or a similar library, we can dynamically set these on each route . This ensures that even though we have a React SPA, each major section has unique metadata. We’ll also include Open Graph tags for sharing (so that, for instance, sharing the home page on social media shows a nice preview image and tagline).
	•	Semantic HTML: We will structure our JSX with semantic elements (<header>, <nav>, <main>, <section>, <footer>, etc.) to aid SEO and accessibility . For example, the home page hero will be in a <section> with proper heading tags for the slogan. Lists of content (like gallery items) will use appropriate markup. This helps search engines understand the content hierarchy.
	•	Alt Text and Accessibility: All images (especially in the Gallery) will have meaningful alt text . For example, alt=“Custom walnut bookshelf in modern living room – Moduvo project”. This not only improves SEO (since search engines index alt text) but also ensures screen reader users can understand the visual content. We will also ensure color contrasts are sufficient and the site is navigable via keyboard (important for accessibility, which indirectly benefits SEO as well).
	•	Performance Optimization: We aim for fast load times, which is crucial both for user experience and SEO (Core Web Vitals). Steps to ensure performance:
	•	Code splitting: We will split the React app bundle by route using dynamic import() for heavy components (maybe Three.js and AR stuff only when Visualize page is accessed).
	•	Image optimization: Use compressed images in modern formats (WebP/AVIF) for the gallery and home banners, with responsive <img srcSet> or CSS background techniques. We will preload critical above-the-fold images for the home page to avoid layout jank.
	•	Lazy loading: Defer loading of offscreen content. E.g., gallery images load as user scrolls down, not all at once.
	•	Caching: The static assets (JS/CSS bundles, images, models) served via CDN will have caching headers. The Contabo deployment can use Nginx or similar to serve static files efficiently.
	•	Use a build optimizer: since likely we’ll use a tool like Vite or Create React App for React, ensure production build is minified and tree-shaken.
	•	Third-party scripts are minimal: avoid heavy third-party libraries unless necessary. For analytics or fonts, use async loading.
	•	Service workers / PWA: optionally, we could add a service worker to cache assets for offline or faster repeat loads, though not a primary requirement.
	•	Branding and UI Consistency: We’ll incorporate Moduvo’s branding (logo, color palette). The branding should convey luxury: perhaps a dark theme with gold or silver accents, or a modern minimal white theme with black and one highlight color. All pages will use consistent typography (select a webfont that matches the brand feel, and load it quickly with font-display: swap to not block rendering). Little touches like using the brand logo as the favicon and in the header, and including a tagline in the site metadata, will reinforce branding.
	•	Enterprise Feel: The overall polish (no broken links, clear contact information, trust signals like “Over 100 installations completed” etc.) will make the site feel production-ready for enterprise clients. We can include a Testimonials section or logos of partner brands (if any) to build credibility. SEO-wise, having a blog or FAQ about modular installations could also help, but not requested explicitly – we focus on the core pages first.

Deployment on Contabo VPS (Dockerized)

While we develop on Replit for convenience, the target production environment is a Contabo VPS 20 (a specific VPS plan likely offering a good CPU/RAM balance). We will prepare for deployment with Docker to ensure a smooth transfer from development to the live server:
	•	Docker Containerization: We will create a Dockerfile to containerize the application. Docker allows us to encapsulate the Node.js backend and the built frontend for easy deployment across environments. Using Docker ensures “it works on my machine” issues are eliminated, as the container includes all necessary dependencies . It also makes scaling or migrating easier, as any Docker host can run the image consistently .
The Dockerfile will likely use a Node base image (e.g., node:18-alpine for a lightweight image). Steps:
	1.	Build the React app – This can be done either outside Docker (and just copy static files in) or inside. A multi-stage Docker build is ideal: first stage uses node:18 to install deps and run npm build for the React app; second stage uses a smaller image (like nginx or node:18-alpine) to serve the app.
	2.	If using an Express server to serve static files and API, we can do a single Node container:
	•	Copy source code,
	•	Install dependencies (npm install),
	•	Run npm run build (for React) which outputs to e.g. build/ folder,
	•	Then run npm run server (which would start the Node app that serves the static build/ and has APIs).
Alternatively, we might use two containers: one for a pure static frontend (NGINX serving the React build) and one for the backend API. But for simplicity, a single container can serve both (Express can serve the static files and proxies API internally). Given our scale, one container is fine.
	•	Contabo Setup: On the Contabo VPS (Ubuntu likely), we will:
	•	Install Docker (or use Contabo’s Docker-ready image) .
	•	Transfer our Docker image. We can either build on Contabo directly using our Dockerfile or build locally and push to a container registry (like Docker Hub or GHCR) and pull on the server.
	•	Run the container (likely via docker run or docker-compose if we add a database container). If using Supabase, we don’t need a DB container since Supabase hosts the DB. If we did self-host, we’d deploy a PostgreSQL container as well.
	•	Ensure it’s running in the background (use -d or a process manager).
	•	Set up a reverse proxy (like Nginx or Caddy) on the VPS to route domain traffic to the container. For example, if our domain is moduvo.com, we’d have Nginx listening on 80/443, forwarding to container port (say 3000). We’d also use Let’s Encrypt to get SSL certificates for HTTPS.
	•	Docker Compose (optional): We may include a docker-compose.yml for convenience. This can define services like the app, a PostgreSQL (if needed), etc. In our case, maybe just one service for the app. But Compose could be handy if we later add more services (like an Nginx service, or a separate admin service, etc.). We’ll include it to simplify running the stack with one command.
	•	No Replit for Production: As specified, we will only use Replit for development and packaging. For production, the Contabo VPS provides more control and power. We ensure nothing in our code is tied to Replit-specific features (like we won’t rely on Repl auth or persistent filesystem except via our own DB). The environment variables for connecting to Supabase (URL, keys) will be provided via a secure mechanism in production (for instance, in Docker we use -e flags or a .env file that Docker reads, but we won’t bake secrets into the image).
	•	Scalability and Monitoring: The VPS can handle our initial load. If traffic grows, we could scale vertically (Contabo higher plan) or horizontally (run multiple containers behind a load balancer, though beyond initial scope). We should implement basic logging in the Node server (console logs at least, or integrate something like Winston for file logs) and use a process manager or Docker’s restart policies to keep the app running. Monitoring can be as simple as uptime robot hitting a health endpoint.
	•	Docker Config Summary: The Docker container will expose port 3000 (or 80 internally). We’ll include any needed configurations like:
	•	Set NODE_ENV=production inside container for performance.
	•	Possibly run npm prune --production to remove dev deps in final image.
	•	Use a non-root user in Docker for security (optional best practice).
	•	The image will be based on an LTS Node which ensures compatibility.

By containerizing, deployment is “one-click” in the sense of running the container on the VPS. It also simplifies environment parity between development (we can even run the same container on Replit if needed) and production, making the launch more reliable and consistent .

Security & Data Protection

Throughout the development of Moduvo’s platform, we prioritize data security and privacy:
	•	Authentication Security: As mentioned, if using Supabase Auth, we leverage their hardened authentication system (JWT-based, with secure password handling) . All communication with Supabase (auth and data) is over HTTPS. If we manage auth in-house, we will use industry-standard methods: bcrypt for password hashing, JWT for tokens with proper expiration, and secure cookie options (HTTPOnly, Secure, SameSite) if we use cookies.
	•	Authorization & Data Isolation: Each user’s data (designs, quotes) is protected so no other user can access it. With Supabase and RLS, this is enforced at the DB query level . In a custom API, we ensure every request that fetches or modifies user-specific data verifies the JWT token’s userID against the target resource’s owner. For example, when requesting a saved design, the backend checks that the design.user_id matches the authenticated user’s id, otherwise returns 403 Forbidden.
	•	Validation & Sanitization: All input from users (e.g., design configurations, profile info, etc.) will be validated. The configurator UI largely restricts inputs to predefined options (so minimal free-form text except maybe user’s name or address). Nonetheless, we sanitize any data before using it (to prevent XSS if any of that data is displayed back, and to prevent SQL injection — though using parameterized queries or ORMs mitigates that).
	•	Storage Security: If users upload any images (room photos), those are stored in a secure bucket. Supabase Storage, for example, can enforce that only the owning user (or admins) can access certain files. We can generate signed URLs for files if needed. For AR models, those are public assets on CDN; that’s fine because they’re not sensitive. But user-uploaded content should not be publicly accessible by URL without auth. We will configure bucket policies accordingly.
	•	HTTPS Everywhere: The site will be served only over HTTPS in production, especially since we handle login credentials and personal data. WebXR also requires a secure context (HTTPS) to work . We’ll ensure our Contabo setup includes TLS (free from Let’s Encrypt). Replit by default provides HTTPS in development.
	•	Profit Calculations & Financial Data: The quote engine’s logic will reside server-side, preventing users from manipulating price calculations on the client. This ensures the integrity of quotes. Also, by centralizing in backend, if we need to adjust pricing formulas, we can do so in one place. We might log quote calculations for audit – e.g., keep a record of what cost inputs and margin resulted in what price, in case we need to justify or debug later.
	•	Admin Access: The admin panel will not be publicly advertised. We could host it under a separate subdomain or simply behind the admin login. We may implement 2FA for admin logins or at least very strong passwords, given the sensitivity (they can see user data and change pricing). All admin actions that alter data will be restricted and possibly logged (e.g., if an admin changes a price, we log which admin did it and when).
	•	Docker & Server Security: On the server, we will keep the system updated, use firewall rules (e.g., only expose necessary ports), and perhaps run the Docker container as an unprivileged user. We’ll also consider rate limiting on APIs (to avoid abuse, e.g., someone spamming quote generation – though not highly sensitive, it could load the system). Using a library or reverse proxy for rate limiting (e.g., Nginx can rate limit or an express middleware) can mitigate DOS attempts.
	•	Low-cost Infrastructure Utilization: Contabo is a cost-effective host; we’ll optimize usage by using a single VPS for everything (as opposed to many cloud services). Supabase itself has a free tier that might cover initial usage (with limits on certain amount of data and requests – we should monitor that). If needed, upgrade Supabase to a paid plan for more capacity, but it’s generally affordable compared to rolling our own full backend infrastructure. By using Supabase, we offload a lot of security and maintenance of auth and DB (they handle updates, backups to some extent, etc.), which reduces our ops burden and cost. The VPS handles the app serving, and since Node and static file serving are not too heavy, a moderate VPS is enough for quite a number of simultaneous users. We avoid Firebase or others that might incur higher costs at scale; with Supabase/Postgres we can potentially self-host in future if needed.

Finally, the goal is that the Replit project can run the entire stack for development/demo: we can configure Replit to run a dev server for React and an Express server together (using something like npm run start:dev that uses concurrently to run both). On Replit, one might just see the app at a given URL as if it were deployed. Then, for production, we follow the Docker deployment steps described. The outcome will be a fully operational Moduvo platform, ready for real-world users to visualize modular designs in AR, customize products, get instant quotes, and engage with the Moduvo team for their installation – all delivered through a seamless, modern web experience.
